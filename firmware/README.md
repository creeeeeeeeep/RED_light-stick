# 크라운 응원봉 펌웨어

Waveshare **ESP32-S3-Matrix** (8x8 WS2812 + QMI8658C 6축 IMU) 용 ESP-IDF 프로젝트.
흔드는 모션 3가지를 인식해서 각각 다른 LED 이펙트를 재생한다.

| 제스처 | 동작 | 이펙트 | 큐 색상 |
|---|---|---|---|
| `SWAY_LR` | 양옆으로 흔들기 | 청록 세로 막대가 좌우 왕복 (잔상 꼬리) | 청록 |
| `PUMP_UD` | 위아래로 찍기 | 마젠타 가로 막대가 아래→위로 솟구치고 상단에서 터짐 | 마젠타 |
| `VIGOROUS` | 격하게 흔들기 | 무지개 스크롤 + 흰색 스트로브 + 스파클 | 주황 |
| `IDLE` | 정지 / 미미한 움직임 | 호박색 숨쉬기 | — |

이펙트의 속도와 밝기는 움직임 세기(`intensity`)에 비례해서 변한다.

## 동작 컨셉 — 쌓았다가 버튼으로 전송

흔들 때마다 바로 보내지 않는다. **흔드는 동안 이모티콘이 쌓이고, 버튼을 누르면
한 번에 전송된다.**

```
흔든다  →  0.7초마다 큐에 1개씩 쌓임 (최대 8개)
           매트릭스 아래쪽부터 한 줄씩 채워짐 (제스처별 색상)
           가득 차면 전체가 숨쉬듯 맥동 = "보낼 준비 됨"
버튼    →  흰 섬광 후 아래로 쓸려나가는 연출, 큐 비움
```

이 방식이 흔들 때마다 전송하는 것보다 나은 이유:

- **채팅 도배 제한과 싸울 일이 없다.** 메시지가 버튼 누를 때만 나간다.
- 치지직은 한 메시지에 이모티콘을 여러 개 넣을 수 있으므로, 쌓은 만큼
  한 줄에 몰아서 표현된다.
- 팬이 언제 보낼지 직접 정한다.

큐가 가득 차면 더 흔들어도 쌓이지 않는다 (먼저 쌓은 게 밀려나면 혼란스럽다).

### 한 메시지에 몇 개까지?

개수보다 **글자 수**가 먼저 걸린다. 이모티콘 하나가 `{:ID:}` 형태로 들어가
`ID 길이 + 4` 자를 먹는다.

| 이모티콘 | 토큰 길이 | 100자 기준 최대 |
|---|---|---|
| `d_1` | 7자 | 8개 |
| `redredLight` | 15자 | 6개 |
| `redredCrownlight` | 20자 | 5개 |

실제 상한은 미확인. 확장의 `crown.setLimits()` 로 올려가며 찾은 뒤
`QUEUE_MAX` 를 맞추면 된다.

## 1. 빌드 / 플래시

> **경고 — 경로에 한글이 있으면 빌드가 깨진다.**
> ESP-IDF 툴체인(CMake/Ninja/xtensa-gcc)은 Windows에서 비ASCII 경로를 제대로
> 다루지 못한다. 이 폴더는 `<프로젝트 폴더>\` 아래에 있으므로
> **빌드 전에 ASCII 경로로 복사할 것.**
>
> ```bash
> xcopy /E /I "<프로젝트 폴더>\firmware" "C:\esp\cheerstick"
> ```

ESP-IDF는 아직 설치돼 있지 않다. v5.2 이상을 설치한 뒤(설치 경로도 ASCII로),
ESP-IDF PowerShell/CMD 환경에서:

```bash
idf.py set-target esp32s3
```

```bash
idf.py build flash monitor
```

보드에 USB-UART 칩이 없어 USB-Serial-JTAG를 콘솔로 쓴다 (`sdkconfig.defaults`에
설정됨). 플래시가 안 잡히면 BOOT 버튼을 누른 채 USB를 연결해 다운로드 모드로
진입시킨다.

## 2. 핀 설정

`main/board_config.h` 한 곳에 모여 있다.

| 항목 | 기본값 |
|---|---|
| WS2812 데이터 | `GPIO14` |
| IMU SDA / SCL | `GPIO11` / `GPIO12` |
| IMU 주소 | 0x6B → 0x6A 순으로 자동 탐색 |
| 전송 버튼 | `GPIO0` (보드 내장 BOOT 버튼) |

버튼은 기본값이 내장 BOOT 버튼이라 **배선 없이 바로 테스트된다.** 크라운
케이스의 버튼 캡(`06_btncap`)에 택트 스위치를 달았다면 `BUTTON_GPIO` 를 그 핀으로
바꾸고 스위치 반대편을 GND 에 연결한다 (내부 풀업을 켜므로 눌림 = LOW).

부팅하면 I2C 전체 스캔 결과를 로그로 찍는다. 여기에 아무것도 안 잡히면 배선이나
핀 번호 문제다. IMU를 못 찾으면 매트릭스에 **빨간 X**가 깜빡인다.

### 화면 방향이 이상할 때

`board_config.h`의 세 값을 조정한다.

- 좌우 스윕이 톱니처럼 찢어짐 → `MATRIX_SERPENTINE` 을 0↔1 뒤집기
- 위로 솟구쳐야 할 이펙트가 아래로 흐름 → `MATRIX_FLIP_Y` 를 1로
- 좌우가 반대 → `MATRIX_FLIP_X` 를 1로

### 밝기와 전류

`LED_MAX_BRIGHTNESS` 기본 60. 64픽셀 풀화이트 기준 최악 약 0.9A이고, 실제
이펙트 평균은 0.2~0.4A다. USB 500mA 급전이면 60이 상한선이고, 배터리 + 2A
컨버터를 쓰면 100 이상도 된다.

거꾸로 이 값을 40 밑으로 내리면 남는 PWM 계조가 부족해서 IDLE 숨쉬기와 잔상
꼬리가 통째로 검게 뭉개진다. 더 어둡게 하고 싶으면 `LED_GAMMA`도 같이 낮출 것.

## 3. 인식 원리

보드가 봉 안에 **어떤 각도로 장착되든** 동작하도록 축을 고정하지 않았다.

1. 자이로로 회전을 예측하고 가속도로 보정하는 상보필터로 중력 방향 단위벡터를
   추정한다.
2. 중력을 뺀 선형가속도를 **중력축 성분(V)** 과 **수평면 성분(H)** 으로 분해한다.
   - 상하로 찍기 → V 우세
   - 좌우로 흔들기 → H 우세
3. 0.8초 슬라이딩 윈도우에서 RMS / 피크 / 자이로 RMS / 스트로크 수를 뽑아
   규칙으로 분류한다.
4. 격한 흔들기는 축과 무관한 에너지 임계로 최우선 판정한다.

### 왜 이렇게 복잡한가

단순한 구현이 실패하는 지점들을 시뮬레이션으로 확인하고 하나씩 막은 결과다.
아래는 전부 실제로 관측된 실패이고, 각 대응은 `gesture.c` 주석에 이유가 적혀 있다.

| 관측된 실패 | 원인 | 대응 |
|---|---|---|
| 좌우/격하게가 전부 IDLE (스트로크 0회) | 호를 그리며 흔들면 원심가속도 때문에 `\|a\|`가 절대 0 근처로 안 떨어져, 크기 기반 슈미트 트리거가 재무장되지 않음 | 스트로크를 크기가 아니라 **방향 반전**으로 검출 (수직은 부호 반전, 수평은 벡터 내적 반전) |
| 중력 추정 오차 최대 156°, 6초 뒤에도 120° | 가속도 신뢰 게이트가 흔드는 동안 완전히 닫혀 한번 틀어지면 영영 복구 안 됨 | 저역통과 가속도를 향한 **느린 보정** 상시 추가 (진동의 한 주기 평균은 중력) |
| 격하게 흔들면 추정이 169°로 뒤집힘 | 원심가속도(4g)가 중력(1g)을 압도해 `a_slow`가 중력이 아니게 됨 | `\|a_slow\|`가 1g 근처일 때만 느린 보정 적용 (크기 게이트) |
| 3Hz 부근에서만 오차 54° (더 격한 4Hz는 10°) | 크기 게이트가 **반쯤 열려** 편향된 방향을 그대로 따라감 | 저역통과 각속도로 **회전 게이트** 추가 |
| 그래도 8초에 36° 누적 | 빠른 보정이 샘플의 5%만 새도 충분. `\|a\|`가 매 주기 1g를 스쳐 지나가는데 그 순간 방향은 중력과 무관 | 순간 `\|a\|`가 아니라 저역통과 **진동 크기**로 정숙도 게이트 |
| 격하게→상하 전환이 2초 넘게 먹통 | 위 오차의 후속 영향 | 위 수정으로 해소 (전환 0.8초) |
| 봉을 툭 내려놓는 동작이 모션으로 인식 | 단발 충격도 에너지는 큼 | **파고율(peak/rms)** 상한 — 지속 진동은 1.3~2.3, 단발은 훨씬 큼 |

## 4. 검증 상태

**빌드는 검증하지 못했다.** 이 PC에 ESP-IDF도, C 컴파일러도 설치돼 있지 않다.
컴파일 오류가 남아 있을 수 있다.

대신 제스처 알고리즘을 Python으로 포팅하고, 강체 응원봉을 시뮬레이션해
IMU가 실제로 볼 (가속도, 자이로) 시퀀스를 만들어 분류기를 검증했다.
시뮬레이터: `<임시 폴더>\claude\...\scratchpad\sim.py`

**45개 시나리오 중 43개 통과.**

통과 항목:
- 3가지 모션 × 세기 3단계 (약/보통/강) — 전부 정확히 분류
- 오인식 방지: 정지 / 봉 들고 걷기 / 단발 충격 — 전부 IDLE
- **방향 불변성**: 보드 장착각 4종(Z 90°, X 90°, 뒤집힘, 임의 37/52/15°) — 전부 동일 결과
- **사람다운 불규칙 모션**: 주파수 지터 + 진폭 변동 ±30% + 2고조파 + 축 비정렬
- **모션 전환**: 좌우→격하게→상하→정지 15초 시퀀스, 각 구간 100% 정확, 전환 지연 0.8초
- **중력 추정 정확도**: 정지 상태 부팅 후 모든 모션에서 8초간 **2.2° 이내**

실패 2건 (동일 원인):
- 이미 흔들고 있는 상태에서 전원이 들어오는 조건에서 좌우가 VIGOROUS로 오분류.
  초기 중력 평균이 오염되고, 흔드는 동안 보정 게이트가 닫혀 회복이 느리기 때문
  (105° → 6초 후 21°, 계속 수렴 중).
- 펌웨어는 이 상태에 **구조적으로 진입하지 않는다.** 부팅 시 정지 상태가 확인될
  때까지(최대 10회) 캘리브레이션을 반복한 뒤에야 엔진을 시작한다. 시뮬레이터에는
  그 대기 로직이 없어서 남은 실패다.
- 그래도 자체 회복은 되며, 안전망으로 발산 감지 후 강제 정렬 로직도 넣어 뒀다.

시뮬레이션은 이상적인 강체 모델이라 **실물 튜닝은 반드시 필요하다.** 특히 봉의
무게와 길이, 사용자의 손목 습관에 따라 절대 가속도 크기가 달라진다.

## 5. 실물 튜닝

`GESTURE_TUNE_LOG`(기본 1)가 켜져 있으면 50ms마다 CSV가 나온다.

```
TUNE,<ms>,<제스처>,<V>,<H>,<전체RMS>,<피크>,<자이로RMS>,<스트로크>,<기울기>
```

`idf.py monitor` 출력을 파일로 받아서 각 모션을 10초씩 해 보고, 실제 값 분포를
보고 `gesture.c`의 `gesture_default_config()`를 조정한다.

가장 자주 건드릴 값:

| 증상 | 조정 |
|---|---|
| 좀 신나게 흔들었는데 바로 VIGOROUS로 튐 | `vig_rms_g` / `vig_peak_g` 올리기 |
| 아무리 격하게 흔들어도 VIGOROUS가 안 뜸 | 위 두 값 내리기 |
| 좌우/상하가 서로 헷갈림 | `axis_ratio` 올리기 (1.35 → 1.6). 대신 애매한 구간이 늘어 반응이 둔해진다 |
| 약하게 흔들면 반응이 없음 | `idle_rms_g` 내리기 (0.12 → 0.08) |
| 가만히 있는데 이펙트가 뜸 | `idle_rms_g` 올리기, `min_strokes` 를 3으로 |
| 반응이 느림 | `confirm_ticks` 내리기 (3 → 2), `hold_ms` 내리기 |
| 이펙트가 팔랑거림 | `confirm_ticks` / `hold_ms` 올리기 |

시뮬레이션 기준 각 모션의 대략적인 전체 RMS 값 (참고용):

| 모션 | 전체 RMS |
|---|---|
| 걷기 | 0.09 g |
| 좌우 (약~빠름) | 0.2 ~ 1.3 g |
| 상하 (약~강) | 0.2 ~ 1.5 g |
| 격하게 | 4 ~ 20 g |

## 6. 파일 구성

```
firmware/
├── CMakeLists.txt
├── sdkconfig.defaults
└── main/
    ├── board_config.h      핀 / 밝기 / 샘플링 레이트 — 여기만 고치면 되는 것들
    ├── qmi8658.[ch]        IMU 드라이버 (I2C, ±16g / ±2048dps / 500Hz / LPF 27Hz)
    ├── ws2812_matrix.[ch]  RMT 커스텀 인코더 기반 매트릭스 (외부 컴포넌트 의존 없음)
    ├── gesture.[ch]        중력 추정 + 축 분해 + 분류기  ← 알고리즘의 전부
    ├── led_effect.[ch]     제스처별 이펙트 렌더링
    └── main.c              I2C 초기화, 캘리브레이션, IMU/LED 두 태스크
```

IMU 태스크는 코어 1에 200Hz로 고정(Wi-Fi 작업과 타이밍 충돌 회피), LED 태스크는
코어 0에 60Hz.

## 7. 아직 안 한 것

- **빌드 검증** (§4 참고)
- **중계 서버 연결** — 버튼을 누르면 지금은 시리얼 로그만 남는다
  (`main.c` 의 `handle_flush()`). 여기서 큐 내용을 서버로 보내면 확장이
  받아서 채팅에 쏘는 구조가 완성된다.
- **제스처 → 이모티콘 ID 매핑** — 펌웨어는 제스처 종류만 들고 있고, 실제
  이모티콘 ID 로의 변환은 서버나 확장 쪽에서 하는 편이 낫다. 이모티콘을
  바꿀 때마다 봉을 다시 플래시할 수는 없기 때문이다.
- Wi-Fi / 블루투스 — 보드에 있지만 이 펌웨어는 쓰지 않는다. 여러 봉 동기화나
  앱 제어를 붙이려면 추가 작업 필요.
- 버튼 입력 — `CROWN_v12`에 `06_btncap`이 있는 걸 보면 물리 버튼이 있는
  설계인데, 어느 GPIO에 물릴지 아직 정해지지 않아 다루지 않았다.
- 배터리 전압 측정 / 저전력 모드.
